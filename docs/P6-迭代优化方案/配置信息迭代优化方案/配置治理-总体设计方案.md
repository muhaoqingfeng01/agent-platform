# 配置治理 — 总体设计方案

> **版本**: V1.0.0
> **日期**: 2026-07-14
> **类型**: 架构设计（仅方案，不做代码开发）
> **涉及模块**: common → infrastructure → bootstrap
> **前置依赖**: Nacos 配置中心已部署（`application.yml` 已配置连接）

---

## 一、背景与目标

### 1.1 现状问题

经全项目扫描，当前配置管理存在以下问题：

| 问题 | 数量 | 影响 |
|------|:----:|------|
| `static final` 硬编码常量 | ~35 项 | 改参数必须改代码 + 重新编译部署 |
| `@Value` 注入但无 `@RefreshScope` | 15 项 | 改配置需重启应用 |
| `@ConfigurationProperties` 无热刷新 | 4 个类 / 44 字段 | 同上 |
| RAG 参数双写（YAML + 硬编码） | 4 项 | 配置不一致风险 |
| SSE 心跳重复硬编码 | 2 处 | 改一处漏一处 |
| `@RefreshScope` 使用 | **0 处** | Nacos refresh-enabled 形同虚设 |
| 自定义 `NacosConfig<T>` 框架使用 | **1 处**（test 包） | 生产未启用 |

### 1.2 治理目标

```
变更配置 → 无需重启 → 实时生效 → 可追溯 → 可回滚
```

### 1.3 设计原则

| 原则 | 说明 |
|------|------|
| **最小侵入** | 优先复用已有 `NacosConfig<T>` 框架，不改 Spring 生命周期 |
| **渐进式** | 按 ROI 分 5 批次，每批独立可交付 |
| **兜底优先** | Nacos 不可用时回退到 YAML 默认值，不阻塞启动 |
| **凭证不进 Nacos** | API Key / 密码只走环境变量 |
| **Sentinel 走原生** | 流控规则用 Sentinel Dashboard，不重复放进 Nacos |

## 五、风险与应对

| 风险 | 等级 | 应对措施 |
|------|:----:|----------|
| Nacos 不可用时应用启动失败 | 🟠 中 | 配置类 `@PostConstruct` 中 catch 异常不抛；业务代码判空 fallback YAML 值 |
| 配置格式错误导致运行时异常 | 🟠 中 | `parseConfig()` 已有 try-catch；增加配置校验（如范围检查） |
| 线程池参数热更新不生效 | 🟡 低 | `ThreadPoolExecutor` 原生支持 `setCorePoolSize`/`setMaximumPoolSize`；队列容量需重启生效，在文档中注明 |
| `@Scheduled` 间隔无法热更新 | 🟠 中 | 用 `TaskScheduler` 动态调度替代 `@Scheduled` 固定周期（子方案 01 详细设计） |
| 配置回滚困难 | 🟡 低 | Nacos 原生支持配置历史版本一键回滚 |

### 7.2 现有 NacosConfig 框架关键代码位置

| 文件 | 路径 |
|------|------|
| 抽象模板 | `infrastructure/.../config/nacos/NacosConfig.java` |
| 测试示例 | `infrastructure/.../config/nacos/test/AiModelConfig.java` |
| Nacos 配置 | `bootstrap/src/main/resources/application.yml:25-36` |
| Nacos 依赖 | `bootstrap/pom.xml:49-57` |

### 7.3 遵循的 DDD 约束

- Nacos 配置类放 `infrastructure/config/nacos/`（基础设施层）
- 静态常量类放 `common/constant/`（通用层）
- 业务代码通过 infrastructure 的配置 Bean 获取配置值
- Application 层通过 `@Value` 或注入 Config Bean 读取，不直接依赖 Nacos SDK
