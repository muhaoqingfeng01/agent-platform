## 一、设计目标

### 1.1 现阶段核心设计目标

本设计方案围绕以下三大核心目标展开，确保系统在满足当前业务需求的同时，具备面向未来的演进能力：

#### 1.1.1 可维护性目标
- **代码结构清晰化**：建立层次分明的模块化架构，确保各模块职责边界明确，降低代码理解与修改成本
- **变更影响面可控**：通过松耦合设计，使单一功能的修改或增强仅影响局部模块，避免牵一发而动全身
- **技术债务可控**：建立统一的编码规范、设计范式与代码审查机制，遏制技术债务的累积
- **文档与代码同步**：确保架构设计文档、接口契约文档与代码实现保持一致性，降低人员更替带来的知识流失风险

#### 1.1.2 可扩展性目标
- **新模式快速接入**：支持新增交互模式（如智能对话、知识库检索、数据分析、任务执行等）以插件化方式接入，无需改动核心框架代码
- **水平扩展能力**：系统支持无状态化设计，各服务实例可水平扩展以支撑业务量增长
- **功能渐进增强**：允许对已有模式进行功能迭代升级，支持多版本共存与平滑过渡
- **第三方集成能力**：预留标准化的扩展点，便于未来与外部系统（如企业级应用、第三方AI服务）进行集成对接

#### 1.1.3 稳定性目标
- **故障隔离与容错**：确保单个模式的异常或故障不会影响其他模式的正常运行，实现故障域的隔离
- **优雅降级机制**：在依赖服务（如LLM服务、向量数据库）不可用时，系统能够提供有损但可用的降级服务
- **流量防护能力**：具备限流、熔断、超时控制等流量治理能力，防止系统过载
- **可观测性保障**：建立完善的监控告警、链路追踪与日志体系，确保问题可感知、可定位、可追溯
- **数据一致性保障**：在分布式环境下，确保关键业务操作的数据最终一致性

### 1.2 设计原则与目标的对齐

| 设计原则 | 对应目标 | 落地措施 |
|---------|---------|---------|
| **开闭原则** | 可扩展性 | 策略模式 + 工厂模式实现，新增模式无需修改现有代码 |
| **单一职责原则** | 可维护性 | 每个策略类只负责一种模式的完整业务逻辑 |
| **依赖倒置原则** | 可维护性 + 可扩展性 | 面向接口编程（Domain 层定义接口，Infrastructure 层实现） |
| **接口隔离原则** | 可维护性 | 提供粒度适中的接口（TaskHandler / InputFilter / VariableResolver），避免冗余方法污染 |
| **故障隔离设计** | 稳定性 | 模式级资源隔离、独立超时与重试配置 |
| **防御式编程** | 稳定性 | 输入校验（BizAssert）、异常捕获（BusinessException）、兜底返回值设计 |

## 二、整体架构分层设计

### 2.1 系统分层架构（对齐 DDD 六模块架构）

采用 **DDD 四层架构** 模型（六模块映射），自上而下依次为：

```
┌──────────────────────────────────────────────────────────────┐
│  bootstrap (启动模块)                                         │
│  @SpringBootApplication + @EnableAsync                       │
├──────────────────────────────────────────────────────────────┤
│  interfaces (接入层) — agent-platform-interfaces              │
│  Controller + Request/Response DTO + ExceptionHandler         │
│  职责：统一路由入口、协议适配（REST/SSE/WebSocket）、参数校验、鉴权拦截 │
├──────────────────────────────────────────────────────────────┤
│  application (应用层/调度层+执行层) — agent-platform-application │
│  AppService + 识别器链 + 策略工厂 + 管线编排 + DTO             │
│  职责：模式识别与路由、策略调度、请求上下文构建、业务编排          │
├──────────────────────────────────────────────────────────────┤
│  domain (领域层) — agent-platform-domain                      │
│  实体+值对象+聚合根+Repository接口+DomainService+TaskHandler   │
│  职责：核心业务规则、领域不变式、策略抽象接口                     │
├──────────────────────────────────────────────────────────────┤
│  infrastructure (基础设施层) — agent-platform-infrastructure   │
│  PO+Mapper+RepositoryImpl+Config+RAG+Metrics+Observability    │
│  职责：实现 Domain 层接口、通用能力支撑、外部系统集成             │
├──────────────────────────────────────────────────────────────┤
│  common (公共模块) — agent-platform-common                     │
│  Result+Exception+BizAssert+PageResponse+IdGenerator+值对象基类 │
│  职责：跨模块共享的基础类型和工具类                              │
└──────────────────────────────────────────────────────────────┘
```

### 2.2 分层职责矩阵

| 层级 | 职责描述 | 对应设计目标 | 现有实现映射 |
|------|---------|-------------|-------------|

| 支撑能力 | 作用 | 对应目标 | 现有实现 |

## 三、前端设计思路

### 3.1 核心模式选择
采用**策略模式 + 插件化架构**作为前端核心设计范式，将不同交互模式封装为独立的策略模块。

### 3.2 技术栈（对齐项目 P5 规划）

| 技术领域 | 推荐方案 | 选型理由 |
|---------|---------|---------|
| 前端框架 | **React 18+** (Vite) | 成熟的组件化能力，生态丰富，P5 已选定 |
| UI 组件库 | **Ant Design 5.x** | 企业级中后台首选，与项目定位匹配 |
| 前端状态管理 | **Zustand** | 轻量级，支持模块化状态隔离，适合多模式场景 |
| 构建工具 | **Vite** | 快速 HMR，ESBuild 预构建 |
| 虚拟滚动 | **react-window** | 高性能长列表渲染，聊天场景必需 |
| WebSocket | 浏览器原生 `WebSocket` + Spring WebSocket | SSE（流式输出）+ WebSocket（审批推送）双通道 |
| IM 适配 | 企业微信/钉钉 API | P5 已规划企微/钉钉适配器 |

### 3.3 交互容器设计
- **模式无关的容器组件**：仅负责模式实例的挂载与渲染调度，不感知具体业务逻辑
- **统一状态管理**：通过 Zustand Store 托管模式切换状态、当前模式上下文数据
- **模式上下文隔离**：各模式拥有独立的状态作用域，避免跨模式状态污染

### 3.4 数据流设计
采用**单向数据流**架构：
> 用户操作 → 模式处理器 → 统一 API 网关(Controller) → ApplicationService → DomainService → Repository → 响应数据 → 模式渲染器 → 视图更新

其中 SSE 流式通道为：
> 用户输入 → POST /api/v1/conversations/{id}/messages → StreamOrchestrationService → SSE token 流 → 前端逐字渲染

### 3.5 扩展机制
- **配置文件驱动**：通过 JSON Schema 声明式定义模式元数据（名称、图标、入口参数结构）
- **模块热插拔**：支持运行时动态注册/注销模式模块
- **降级呈现**：当某模式模块加载失败时，自动回退至默认提示界面

## 四、后端设计思路

### 4.1 核心设计范式

采用**策略工厂模式 + 责任链模式 + 模板方法模式**作为后端核心架构基础，与项目现有设计模式无缝衔接：

| 模式 | 用途 | 现有实现参考 |
|------|------|-------------|
| **责任链模式 (Chain of Responsibility)** | 请求处理管道：意图识别链、安全过滤链 | `IntentRecognitionChain`（Rule→Cache→LLM）、`SecurityFenceApplicationService`（Injection→Jailbreak→Sensitive→Length） |
| **策略工厂模式 (Strategy + Factory)** | 多模式行为封装：切片策略、工具调用策略 | `ChunkStrategyFactory` + 7 种 `ChunkStrategyService` 实现 |
| **模板方法模式 (Template Method)** | 通用流程骨架：记忆提取、任务执行 | `MemoryExtractor` 体系、`TaskHandler<T>` 接口 |
| **观察者模式 (Observer)** | 流式输出、领域事件 | SSE 流式回调（doOnNext/doOnComplete/doOnError） |
| **状态模式 (State)** | 生命周期管理 | `ConversationStateMachineConfig`（Spring StateMachine） |
| **Memento 模式** | 版本快照与回滚 | `PromptTemplateVersion`（提示词版本管理） |
| **门面模式 (Facade)** | 模块统一入口 | 各 `ApplicationService` 封装编排逻辑 |
| **仓储模式 (Repository)** | 数据访问抽象 | 23 个 Repository 接口 + MyBatis 实现 |

### 4.2 策略层设计

#### 4.2.1 策略抽象基类（对齐 `TaskHandler<T>` 模式）

```java
/**
 * 交互模式策略接口 — 策略模式核心抽象.
 * <p>
 * 每种交互模式（智能对话、知识检索、任务执行、分析推理等）实现此接口，
 * 通过 @Component 自动注册到 InteractionModeFactory。
 *
 * @param <T> 请求载荷类型
 * @param <R> 响应结果类型
 */
public interface InteractionStrategy<T, R> {

    /** 模式标识（对应 IntentResult.intentCode） */
    String getModeCode();

    /** 模式名称 */
    String getModeName();

    /** 前置校验：验证请求参数的合法性与完整性 */
    void validate(T request);

    /** 前置处理：请求数据的预处理与转换 */
    T preProcess(T request);

    /** 执行核心逻辑 */
    R execute(T request, InteractionContext context);

    /** 后置处理：响应数据的格式化与增强 */
    R postProcess(R response);

    /** 降级处理：依赖服务不可用时的兜底逻辑 */
    R fallback(T request, Throwable error);

    /** 优先级（多个策略匹配同一模式时取最高优先级） */
    default int getPriority() { return 0; }
}
```

#### 4.2.2 策略工厂（对齐 `ChunkStrategyFactory` 模式）

```java
/**
 * 交互模式策略工厂 — 自动发现与调度.
 * <p>
 * 通过 Spring InitializingBean 自动收集所有 InteractionStrategy 实现，
 * 根据意图识别结果路由到对应策略。
 */
@Component
public class InteractionStrategyFactory implements InitializingBean {

    private final Map<String, InteractionStrategy<?, ?>> strategyMap = new ConcurrentHashMap<>();
    private final List<InteractionStrategy<?, ?>> strategies;

    @Override
    public void afterPropertiesSet() {
        // 自动收集所有 InteractionStrategy Bean，按 modeCode 注册
        strategies.forEach(s -> strategyMap.put(s.getModeCode(), s));
    }

    /** 根据模式编码获取策略 */
    public InteractionStrategy<?, ?> getStrategy(String modeCode) {
        InteractionStrategy<?, ?> strategy = strategyMap.get(modeCode);
        if (strategy == null) {
            throw new BusinessException(400, "不支持的交互模式: " + modeCode);
        }
        return strategy;
    }
}
```

#### 4.2.3 策略实现示例分类（对齐现有模块）

| 模式类型 | modeCode | 功能描述 | 现有实现基础 | 扩展场景 |
|---------|----------|---------|-------------|---------|
| **对话交互型** | `conversation` | 多轮对话、上下文管理、SSE流式输出 | `StreamOrchestrationService` + `IntentRecognitionChain` | 智能客服、虚拟助手 |
| **知识检索型** | `knowledge_search` | 向量检索(Milvus)、重排序(Reranker)、结果融合、引用溯源 | `KnowledgeBaseDomainService` + `VectorSearchProvider` + `FulltextSearchProvider` | 企业内部知识库、文档问答 |
| **任务执行型** | `task_execution` | DAG工作流编排、工具调用(MCP)、异步任务提交 | `TaskHandler<T>` + `DagParser` + `McpClientManager` | 自动化流程、报表生成 |
| **分析推理型** | `analysis` | 数据洞察、趋势分析、报告生成 | 待扩展 | 商业智能、决策支持 |
| **安全审批型** | `approval` | 人机协同审批、WebSocket推送 | `ApprovalWorkflowStateMachine` + `ConversationWebSocketHandler` | 敏感操作审批 |

### 4.3 请求处理管道（对齐现有实现）

构建**可编排的中间件管道**，依次完成：

```
请求 → [1.认证鉴权] → [2.限流熔断] → [3.安全过滤] → [4.意图识别] → [5.模式路由] → [6.策略执行] → [7.输出脱敏] → 响应
       Sa-Token      Sentinel      4层过滤链    3层识别链    策略工厂     Interaction    PiiDesensitizer
                                    (Injection   (Rule→       (Factory)    Strategy       (Presidio)
                                    →Jailbreak   Cache→LLM)               .execute()
                                    →Sensitive
                                    →Length)
```

| 中间件 | 实现组件 | 说明 |
|--------|---------|------|
| **认证鉴权中间件** | `SaTokenWebMvcConfig` + `StpInterfaceImpl` | RBAC 权限模型，租户隔离 |
| **限流熔断中间件** | `SentinelConfig` + `RateLimitAspect` | 租户维度限流，令牌桶算法 |
| **安全过滤中间件** | `SecurityFenceApplicationService.filterInput()` | 4 层 Chain of Responsibility，Aho-Corasick 多模匹配 |
| **意图识别中间件** | `IntentRecognitionChain.recognize()` | 3 层：规则(~1ms) → 缓存(~5ms) → LLM(~500ms)，命中即短路 |
| **路由分发中间件** | `InteractionStrategyFactory.getStrategy()` | 根据意图识别结果路由至对应策略 |
| **输出脱敏中间件** | `SecurityFenceApplicationService.desensitizeOutput()` | Presidio PII 脱敏 |

### 4.4 模式发现与版本管理
- **模式发现机制**：`InteractionStrategy` 实现类标注 `@Component`，由 `InteractionStrategyFactory` 通过 `InitializingBean` 自动收集注册
- **版本兼容策略**：同一模式支持多版本共存（通过 `modeCode` 后缀区分如 `knowledge_search_v2`），实现平滑升级
- **灰度发布支撑**：按租户维度或流量比例进行模式版本灰度（结合 Nacos 动态配置）

### 4.5 容错与稳定性设计

#### 4.5.1 故障隔离
各模式策略运行在独立的执行上下文中，单个模式的异常不影响其他模式的可用性。现有机制：
- 安全过滤链中单个过滤器异常 → `continue`（不阻断后续过滤器）
- 定时任务逐条扫描 → 单条失败不影响后续
- SSE 流式回调异常 → `emitter.completeWithError(error)` 独立处理

#### 4.5.2 超时与重试
- 为每个策略配置独立的超时阈值（`TaskHandler.getTimeoutSeconds()` 默认 120s）
- 支持幂等操作的可配置重试策略（指数退避）
- SSE 心跳机制（15s ping）保持长连接

#### 4.5.3 熔断降级
- 引入 Sentinel 熔断器，当某模式错误率超阈值时自动熔断
- 定义降级策略（`InteractionStrategy.fallback()`）：返回缓存结果、友好提示或路由至备用模式

#### 4.5.4 流量控制
- 按租户维度配置独立的限流阈值（`RateLimitAspect`）
- Sentinel 支持令牌桶、滑动窗口等多重限流算法

### 4.6 数据一致性保障
- **请求上下文传递**：`TraceFilter` 生成 traceId/spanId/requestId + `TenantContext` ThreadLocal 透传租户信息
- **事务边界界定**：`@Transactional` 明确标注事务范围，区分强一致性与最终一致性操作
- **补偿机制**：对于长流程操作（如 DAG 任务执行），设计对应的反向补偿逻辑（`TaskHandler.onTimeout()` / `onFailure()`）

### 5.2 模式契约规范
- **请求契约**：标准化请求结构（模式标识 `modeCode`、输入载荷、用户上下文、扩展参数）
  ```java
  public record InteractionRequest(
      String modeCode,           // 模式标识
      String userInput,          // 用户输入
      String conversationId,     // 会话 ID（对话型模式使用）
      Map<String, Object> payload, // 模式特有参数
      Map<String, Object> extensions // 扩展参数
  ) {}
  ```
- **响应契约**：标准化响应结构（成功标识、业务数据、错误信息、元数据）
  ```java
  public record InteractionResponse(
      boolean success,           // 成功标识
      Object data,               // 业务数据
      String errorCode,          // 错误码
      String errorMessage,       // 错误信息
      Map<String, Object> metadata // 元数据（token 数、耗时、引用等）
  ) {}
  ```
- **错误码规范**：统一错误码体系（对齐现有 `Result.java` + 5 异常类体系），便于前端分类处理

## 六、可观测性设计

### 6.1 指标采集维度

| 维度 | 采集内容 | 对应目标 | 现有实现 |
|------|---------|---------|---------|
| **业务指标** | 各模式调用量、成功率、响应时长分布 | 稳定性（健康度感知） | `AgentMetrics` (Micrometer) — messageProcessingTimer, llmCallTimer, tokenConsumption |
| **系统指标** | CPU、内存、网络IO、连接池状态 | 稳定性（资源预警） | Spring Boot Actuator + Micrometer + Prometheus |
| **用户行为指标** | 模式切换频次、停留时长、交互深度 | 可扩展性（需求洞察） | Langfuse LLM 调用追踪 |
| **LLM 调用指标** | Token 消耗、模型延迟、错误率 | 稳定性（依赖监控） | `AgentMetrics.recordTokenConsumption()` + `recordLlmError()` |
| **安全事件指标** | 敏感词命中、注入拦截、越狱检测 | 稳定性（安全态势） | `SecurityEventRecorder` → `t_security_event` 表 |

### 6.2 告警策略
- **SLO告警**：核心模式可用性低于 99.9% 时触发告警（Prometheus AlertManager）
- **异常突增告警**：错误率或响应时长突增时预警
- **容量告警**：资源使用率接近上限时提前通知
- **安全告警**：敏感词/注入/越狱拦截频率异常升高时触发

### 6.3 链路追踪
- 为每个请求生成全局唯一追踪标识（`TraceFilter`: traceId + spanId + requestId）
- 记录请求在各层级的耗时明细，便于瓶颈定位
- Langfuse 记录 LLM 调用的完整 trace（prompt → response → latency → tokens）
- MDC 上下文在 SSE 流式异步回调中显式传递

### 8.1 技术选型原则

1. **不重复造轮子**：优先使用 Spring 生态成熟组件，仅在生态不足时自研（如 Langfuse HTTP Ingestion 直连、TraceFilter）

## 十、总结

本设计方案以**可维护性、可扩展性、稳定性**为三大核心设计目标，通过与项目现有 DDD 架构深度融合，确保设计方案落地可行：

| 设计目标 | 核心架构手段 | 关键落地机制 | 现有实现基础 |
|---------|-------------|-------------|-------------|
| **可维护性** | 策略模式解耦 + DDD 四层架构 + 单一职责原则 | 模式独立封装（InteractionStrategy）、接口契约标准化、Nacos 配置集中管理 | 23 聚合根/实体 + 19 DomainService + 19 AppService |
| **可扩展性** | 工厂模式 + 插件化架构 + 配置驱动 | 新模式实现 InteractionStrategy 接口 + @Component 自动注册、版本共存与 Nacos 灰度发布、水平扩展能力 | ChunkStrategyFactory 模式 + TaskHandler 模式 + InitializingBean 自动收集 |
| **稳定性** | 故障隔离 + Sentinel 熔断降级 + 可观测性体系 | 模式级资源隔离、限流超时控制、Prometheus + Langfuse 全链路监控告警 | SecurityFence 4 层过滤 + Sentinel RateLimitAspect + AgentMetrics + TraceFilter |

该方案通过**策略模式实现业务逻辑的横向解耦**，通过**工厂模式实现模式的统一调度管理**，通过**责任链模式实现请求处理的灵活编排**，在保障系统稳定性的前提下，为未来业务模式的快速扩展提供了坚实的架构基础。
